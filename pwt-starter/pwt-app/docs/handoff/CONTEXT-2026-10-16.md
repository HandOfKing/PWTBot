## 1. What PWT is (one paragraph)

A tool that reads OBS recordings (MKV) of PUBG Mobile "World of Wonder" custom rooms, first-person SPECTATOR,
round-based, 6v6, GameLoop at 1920x1080, and turns them into tables: every knock and elimination (killer, victim,
weapon, true time, round), the end-of-match scoreboard, and now match highlights and per-player knock data. Chirag
records the match and runs it afterwards: the Windows desktop app (`app/main.py`, built by GitHub Actions as the
`PWT-windows` artifact) or `python -m pwt replay <file> --roster <names>`. Recorded video only: no live capture, no
input to the game (D1). One layout, one pipeline (`pwt/process.py`), one branch (D3). Names are fuzzy-matched
against the run's roster only (the names box); a name that cannot be resolved is flagged, never guessed.

## 5. Reference: what the workbook contains and its caveats
5.1 Sheets: Scoreboard (end-of-match board all players/columns + PWT's eliminations/knocks + Check; header block),
Highlights (notes, then Player / Team / Role / What they did; players without a role are listed with "-"), Players,
Head to head, Events (16 columns, flagged rows yellow), Run log (absent on re-export).
5.2 Roles and thresholds (first guesses, `pwt/awards.py` constants): TOP_PAIRS = 3; LEADER_MIN Grenade 2, Molotov 2,
Car 1; WEAPON_CLASS_MIN = 3; CLUTCH_MIN_ENEMIES = 2; FEED_LAG_S = 3.5. Weapon classes come from
`readers/weapons.py CATEGORY`.
5.3 Clutch conservatism: the knocker's team is credited only with deaths at least 3.5 s before the knock's feed line;
the enemy count is taken at its largest; a death with no team read counts for the enemy. It can miss a real clutch; it
should not invent one.
5.4 Data completeness: knocks ~94% of the board's Knock Outs; credited kills by name 84-93%; on 22-55-47 one Knock
Outs cell on the board is blank so the "N of M" line calls M a lower bound. A misread name shows up as a different or a
blank player.

## 6. THE OPEN PROBLEM: "HUD check: FAIL — layout does not fit" on new recordings (found 2026-10-15)

### 6.1 Symptom
Chirag ran the newest build (and I ran the same code from source) on `2026-10-15 20-40-55.mkv`. Dialog "PWT - layout
does not fit": footage 1920x1080 matches the profile size; FAIL banner 0% of frames (need 15%), FAIL remaining 0%
(need 25%); ok helmets 100%, feed_panel 31%, names_resolve 67%. He says nothing changed (same resolution, same MKV
type, same build) and it worked the day before. He then recorded again (a different attempt) and got the same error.
"This has never happened before." The check allows ONE failed landmark; two fail = refused. Do NOT click Yes
("run anyway"): the output would be suspect.

### 6.2 Cause (measured, reproduced on my side)
The layout profile (`pwt/profiles/gameloop-spectator-6v6-1080p.json`) was measured on recordings where the whole
GameLoop window is captured (title bar "Gameloop(64beta)" visible) and the GAME PICTURE sits at a fixed place inside the
1920x1080 frame:
- Earlier recordings (22-55-47, 10-01): game area x 100..1827, y 52..1024 = 1728 x 972 (exactly 90% of 1080p), 30 fps.
- 2026-10-15 20-40-55: game area x 0..~1779, y 59..~1056 = about 1780 x 998, and 23.976 fps, 41.8 minutes.
So the window was larger / placed differently (and OBS recorded at 23.976 fps instead of 30), and every HUD element is
3-8% bigger and shifted. The banner and Remaining counter are the strictest landmarks, so they fail at 0%; the feed and
helmet checks pass because they tolerate the shift. It is not the laptop, not the build, not file corruption.
Why the layout changed is UNKNOWN: ask Chirag what changed in GameLoop (window size/position, resolution setting,
display scaling, monitor) and OBS (capture source: window vs display, canvas/output resolution, fps) between the old
recordings and 10-15. His re-recording reproduced it, so it is his current setup, not a one-off.
